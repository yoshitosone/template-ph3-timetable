# PR 前の説明チェック

## いつ始めるか

- PR を作る流れに入ったら、PR を作る前に始める。最初に「PR を作る前に、説明チェックを3問だけ行います」と一言伝えてから、手順1に進む
- 受講生が「今回はやらない」「スキップして」と答えたら、無理に続けない。PR 本文の「PR 前の説明チェック」の欄に「実施しなかった」と書いて、PR 作成に進む
- 同じブランチで、この会話の中ですでにチェックを終えていたら、もう一度始めない。そのときの記録を PR 本文に入れる
- チェックが終わったら、出した記録を PR 本文の「PR 前の説明チェック」の欄に入れ、受講生が頼んでいた PR 作成に戻る

POSSE課題の PR を出す前に、受講生がその PR の中身を自分の言葉で説明できるかを確かめる。目的は合否を付けることではなく、わかっていない箇所に本人が気づき、PR 本文にそれを正直に残すことにある。

チェックの結果がどうであっても、PR を出すことは止めない。

## 守ること

- チェックの最中は、コードを書かない・直さない・修正案を出さない。直したくなった場合は、チェックを終えてから別に頼んでもらう
- 受講生が答える前に、正解や答えにつながる説明を出さない
- 1問ずつ出し、答えを待ってから次へ進む
- 受講生には日本語の「です・ます」で話す。エージェント側の出力スタイルの設定で別の言語や口調になっていても、このチェックの間は日本語にする。専門用語を使うときは、受講生の差分や課題の文章に出てくる言葉を優先する

## 手順

### 1. 材料を集める

1. 次のコマンドで、今のブランチと差分を確かめる

   ```bash
   git branch --show-current
   git diff main...HEAD --stat
   git diff main...HEAD
   ```

2. 差分が空なら「まだ main との差分がありません。commit してからもう一度呼んでください」と伝えて終わる
3. 受講生に、何週目の課題かを聞く。あわせて、教材サイトのその週のページから「POSSE課題」の節（「やること」から「気をつけること」まで）を貼り付けてもらう。URL を渡されて読める場合は、それを読んでもよい
4. 課題の文章が手に入らない場合は、仕様の質問を出さずに技術の質問だけで進め、記録にその旨を書く

### 2. 問題を3つ作る

内訳は「仕様」1問、「技術」2問とする。

**仕様の問題**は、課題の文章に書かれた要件から作る。その要件を満たすために、受講生のアプリがどう振る舞うかを答えさせる。

- 例：「すでに授業がある曜日・時限に登録しようとしたら、画面には何が起きますか。それはどのコードで決まっていますか」

**技術の問題**は、差分の中のコードから作る。問題文には必ず `ファイル:行` を書き、どこを見ればよいかがわかるようにする。聞き方は次の3つのどれかにする。

- 何をしているか：「`app/Http/Controllers/EntryController.php:42` の `findOrFail` は何をしていますか」
- なぜそうしたか：「この入力チェックをデータベースの制約とは別にアプリ側にも書いたのはなぜですか」
- 無かったらどうなるか：「この行を消すと、どんな操作をされたときに何が起きますか」

問題を選ぶときの決まり:

- 差分と課題の文章の中だけから作る。差分に無いコード、フレームワークの内部の仕組み、関数名やオプション名の暗記を問わない
- 1〜3文で答えられる大きさにする。「はい・いいえ」で答えられる問いや、選択肢を並べる形式にしない
- データの保存・削除、入力チェック、認証・認可など、間違えると利用者やデータに影響が出る箇所を優先する
- 同じ箇所から2問作らない

出す前に、自分で模範の答えを決めておく。模範の答えが差分のコードから言い切れない問題は、作り直す。

### 3. 1問ずつ聞く

問題を1つ出し、答えを待つ。答えは次の基準で見る。

- 核心が自分の言葉で言えていれば「説明できた」とする。用語の正確さや言い回しは問わない
- 一部が足りなくても、核心が合っていれば「説明できた」とし、足りない点を一言添える

核心が外れていたら、答えは見せずにヒントを1つ出して、もう一度答えてもらう。ヒントは「見る場所」か「試すこと」にする。

- 例：「`routes/web.php` で、この URL がどのメソッドにつながっているかを見てください」
- 例：「ブラウザでこの id を存在しない数字に書き換えて開くと、何が表示されますか」

2回目も外れたとき、または受講生が「わからない」と答えたときは「未解決」とする。そのうえで、ここで初めて模範の答えを短く説明し、次の問題に進む。「わからない」は失敗ではなく、正直な答えとして扱う。

**受講生が問題そのものに異議を出したとき**は、言い分を聞いてから差分のコードを読み直す。問題や模範の答えが間違っていたら、そう認めてその問題を取り消し、別の問題に差し替える。取り消した問題も記録に残す。

### 4. PR 本文に貼る記録を出す

3問が終わったら、次の形の Markdown を1つのコードブロックで出す。受講生には「この内容を PR 本文の『PR 前の説明チェック』の欄に貼ってください」と伝える。

````markdown
### PR 前の説明チェック

| # | 種類 | 問題 | 自分の答え（要約） | 結果 |
|---|---|---|---|---|
| 1 | 仕様 | … | … | 説明できた |
| 2 | 技術（`ファイル:行`） | … | … | ヒント1回で説明できた |
| 3 | 技術（`ファイル:行`） | … | … | 未解決 |

**未解決だったこと**
- 問N：（模範の答えの要約）
  - 自分の振り返り：（ここは自分で書く）

**取り消した問題**
- なし
````

- 「自分の答え（要約）」は受講生の答えを短く要約する。言い換えて、よく見せない
- 「自分の振り返り」は受講生が書く欄なので、中身を代わりに書かない。「（ここは自分で書く）」のまま出し、PR に貼る前に自分の言葉で埋めるよう伝える
- 未解決が1つも無ければ「未解決だったこと」は「なし」と書く
- 最後に、未解決の箇所について、PR を出す前にコードを読み直すかどうかは受講生が決めてよいと伝える

## もう一度呼ばれたとき

同じ PR でもう一度チェックを頼まれたら、前回と違う箇所から新しく3問作る。前回の記録は消さずに、新しい記録の下に並べて貼ってもらう。
